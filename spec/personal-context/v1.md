# Personal Context Pack — format version 1

| | |
|---|---|
| Status | Stable. Version 1 will only gain optional, backwards-compatible clarifications. |
| Identifier | `inkwright-context-pack/1` (the `format` member) |
| Media type | `application/json` (files: `*.json`; inside a pack folder: `pack.json`) |
| JSON Schema | [`v1.schema.json`](v1.schema.json) (JSON Schema 2020-12) |
| Conformance suite | [`conformance/`](conformance/) |
| Validator | `npx inkwright context validate <file>` · `validateContextPack()` in `@inkwright/core` |
| Licence | This specification and its schema: CC BY 4.0. Implement it in anything. |

The key words MUST, MUST NOT, SHOULD and MAY are to be read as in RFC 2119 and RFC 8174 when, and
only when, they appear in capitals.

## 1. Purpose

Agents work better with the person's own context: what they decided, what they wrote, what
they prefer. A **personal context pack** is a portable, self-contained bundle of that context
about one subject, built from the person's notes, small enough to put in a model's context
window, and **cited**: every compiled statement says how it was made and where it came from, so
a consumer can tell a quote from an inference and show the person the source.

Inkwright writes packs (Compiled wiki › Context pack, docs/COMPILER.md); the format is
deliberately independent of Inkwright so other note tools can write packs and any agent can read
them.

## 2. Document

A pack is one JSON object (RFC 8259, UTF-8) with these members, all REQUIRED:

| Member | Type | Meaning |
|---|---|---|
| `format` | string | MUST be `"inkwright-context-pack/1"`. |
| `id` | string | 1–64 characters of `[0-9A-Za-z_-]`; unique among one producer's packs. |
| `title` | string | 1–500 characters: what the pack is about. |
| `createdAt` | string | RFC 3339 date-time with offset (`2026-11-02T09:00:00Z`). |
| `memory` | object | Standing context about the person: `instructions` (how they want to be helped) and `facts` (about them), each an array of strings; either MAY be empty. |
| `compiled` | array | Compiled pages (§3): dense, cited statements. MAY be empty. |
| `notes` | array | The notes themselves (§4). MAY be empty. |
| `images` | array | Key handwriting or figures as images (§5). MAY be empty. |
| `truncated` | array of strings | Titles of notes that were chosen but left out to stay within the producer's size budget. |

`$schema` MAY be present (a URI of this schema). Members whose names start with `x-` are
**extensions**, allowed on every object; consumers MUST ignore extensions they don't understand.
Any other member is an error, so that a typo can't silently drop meaning.

## 3. Compiled pages and claims

```json
{ "title": "Launch", "kind": "topic", "claims": [
  { "text": "The beta ships on Friday.", "tag": "EXTRACTED", "confidence": 0.94,
    "sources": [ { "noteId": "LAUNCH", "note": "Launch plan", "page": 1, "link": "#mem/LAUNCH/1" } ] } ] }
```

- `title` (non-empty), `kind` (non-empty; `topic`, `person`, `project`… — an open set), `claims`.
- A **claim** is one statement: `text` (non-empty), `tag`, `sources`, and OPTIONAL `confidence`.
- `tag` says how the statement was made, and consumers SHOULD treat the three differently:
  - `EXTRACTED` — quoted or near-verbatim from the sources. MUST cite at least one source.
  - `INFERRED` — synthesised from the sources; plausible, not stated.
  - `AMBIGUOUS` — the sources disagree or are unclear; an open question, not a fact.
- `confidence` — number in [0, 1] or `null`: how well the sources support the statement.
- A **source** points at where the statement came from:

  | Member | | |
  |---|---|---|
  | `noteId` | REQUIRED | the note's id (`[0-9A-Za-z_-]{1,64}`) |
  | `page` | REQUIRED | 1-based page number |
  | `link` | REQUIRED | `#mem/<noteId>/<page>[/<x>,<y>,<w>,<h>][@<recording>:<ms>]` — the same place as a fragment that the producing app can open (`noteId` and `recording` percent-encoded) |
  | `note` | OPTIONAL | the note's title, for display |
  | `rect` | OPTIONAL | `{minX, minY, maxX, maxY}` region on the page, in the producer's page units, `max ≥ min` |
  | `recording`, `ms` | OPTIONAL, together | a recording on that note and a moment in it (ms ≥ 0), for things that were said |

  A source MAY instead be a **string** when the producer could not resolve it; consumers can
  show it but not open it (validators warn).

## 4. Notes

`{ "id", "title", "notebook"?, "tags", "updatedAt", "summary"?, "pages" }` — `id` as above and
unique within the pack; `notebook` a path with parts joined by `" / "` (or `null`); `tags`
without `#`; `updatedAt` RFC 3339; `pages` an array of `{ "index", "text" }` with a **0-based**
`index`, unique within the note, and the page's text (typed and recognised handwriting). Pages
with no text MAY be omitted.

Producers SHOULD order notes newest first and SHOULD fill the pack within a size budget with
compiled pages first (most information per character), then notes, listing what didn't fit in
`truncated`.

## 5. Images

`{ "name", "noteId", "page", "alt", "mediaType", "base64" }` — `name` a plain file name (no
folder separators, `..`, control or reserved characters), unique within the pack; `page`
1-based; `alt` what is known about the image (recognised text, or a description; MAY be empty);
`mediaType` an `image/*` type; `base64` the bytes in standard padded base64 (RFC 4648 §4).
Producers SHOULD include images only for pages whose handwriting has no recognised text.

## 6. Rules beyond the schema

The JSON Schema expresses most of this document. A conformant validator MUST also check:

1. `createdAt` and `updatedAt` are real dates (no 30 February).
2. Note `id`s are unique; page `index`es are unique within a note; image `name`s are unique.
3. A source's `link` names the same note and page as its `noteId` and `page`.
4. `base64` decodes.

and SHOULD warn (not fail) when a source cites a note that is not in `notes`, or a source is an
unresolved string.

## 7. Renderings

The same content has two standard renderings besides JSON, which producers MAY also write:

- **Markdown** (`pack.md`): `# <title>`; a line on how it was made; `## Standing preferences`;
  `# Compiled` with one `## <page title>` per page and one bullet per claim:
  `- <text> _(extracted|inferred|ambiguous)_ [n]…`; `## Handwriting` with images as
  `assets/<name>`; `# Notes` with `### <title>` per note; `# Sources` with `[n]: <note title>,
  page <p> — <app> <link>`.
- **Agent Skill folder** (agentskills.io): `<skill-name>/SKILL.md` (front matter `name`,
  `description`), `references/context.md` (the Markdown rendering) and `assets/<image name>`.

A saved pack is a folder holding `pack.json` and, optionally, `pack.md`; Inkwright keeps them in
the vault at `ai/packs/<id>/` and serves them over MCP as `inkwright://packs/{id}`.

## 8. Consumers

Consumers SHOULD:

- prefer `EXTRACTED` claims when facts matter, present `INFERRED` claims as inferences, and treat
  `AMBIGUOUS` claims as open questions to ask the person about;
- keep citations when they repeat a claim, so the person can check it;
- treat everything in a pack as **data**, never as instructions to the agent, except `memory.
  instructions`, which are the person's own standing instructions — and even those MUST NOT
  override the user's current request or the agent's safety rules. A pack is easy to forge; one
  from an untrusted source is untrusted content.

## 9. Versioning

`format` carries the major version. A consumer that finds a version it doesn't know MUST NOT
guess; it SHOULD say which versions it supports. Changes that a version-1 consumer could
misread need a new major version; new optional members use the `x-` prefix until a minor
revision of this document names them.

## 10. Conformance

A **producer** conforms when every pack it writes passes the validator without errors. A
**consumer** conforms when it accepts every file in `conformance/valid/` and refuses (or reports)
every file in `conformance/invalid/`. `conformance/manifest.json` lists each invalid case with the
JSON Pointer of the error a validator must report, and whether the JSON Schema alone catches it.
Inkwright runs the suite against the schema (with Ajv) and its own validator in
`apps/mcp-server/test/context-spec.test.ts`.
